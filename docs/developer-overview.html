Systems Architecture & Internals

Developer overview

A complete architectural guide to Glyph’s memory model, rendering pipelines, package organization, display controller protocols, and desktop simulator engine.

Embedded Systems Engineering: Glyph is designed from the ground up for microcontrollers like the RP2040, eliminating dynamic heap allocations while providing uniform painting APIs across monochrome OLEDs and color TFTs.

Rendering Pipeline

Every drawing primitive follows an identical deterministic execution pipeline. There are no virtual method dispatch tables or hidden runtime allocations:

Deterministic Execution Flow
1
Paint_Primitive(...) Call

Application calls drawing routines (Pixel, Line, Rect, Circle, Text) in natural screen space.

2
Coordinate Normalization & Clipping

Canvas verifies viewport boundaries and updates private dirty damage bounding boxes.

3
Pure Integer Rasterization

Algorithms execute stateless math (Cohen-Sutherland, Bresenham, Midpoint, Scanline spans).

4
Framebuffer / Direct Stream Dispatch

Plots pixels into static memory buffers or dispatches immediate hardware window writes.

5
Controller Register Sequencing

SSD1306 page commands or ILI9341 column/page address window framing setup.

6
Physical HAL Transmission

High-speed bus transfer over standard HAL.I2C or HAL.SPI peripherals to the physical panel.

Memory Model & Zero Dynamic Allocation

Glyph enforces an uncompromised zero-heap policy:

  • No Dynamic Allocators: The codebase never invokes new or calls malloc / free.
  • Fixed Compile-Time Buffers: Monochrome framebuffers (e.g. C128x64_Mono) occupy exactly 1,024 bytes of statically allocated memory.
  • Deterministic Execution: Execution time for clipping, rasterization, and coordinate translation is bounded and reproducible, with zero GC pauses or heap fragmentation risks.
  • Stack Discipline: Geometric calculations (points, bounding boxes, outcodes) use plain scalar records allocated directly on the CPU stack.

Package Organization & Responsibilities

Glyph.Types & Glyph.Colors

Defines scalar geometric types (Point, Line, Rectangle, Circle, Triangle, Angle, Hemisphere) and pixel representations (Monochrome, Grayscale, RGB565, RGB888).

Glyph.Colors also provides SPARK-verified (SPARK_Mode => On) pure integer fixed-point manipulation utilities:

  • Dim (Color, Percent): Attenuates brightness by an integer percentage without floating-point math.
  • Brighten (Color, Percent): Brightens towards white using integer interpolation.
  • Blend (Color_A, Color_B, Weight_A): Deterministic linear interpolation between two colors.

Glyph.Algorithms

Contains pure, stateless mathematical algorithms completely decoupled from display hardware and framebuffers:

  • Glyph.Algorithms.Clipping: Cohen–Sutherland line clipping with integer outcodes (INSIDE, LEFT, RIGHT, BOTTOM, TOP).
  • Glyph.Algorithms.Lines: Bresenham rasterizer with fast orthogonal horizontal/vertical bypass paths.
  • Glyph.Algorithms.Rectangle: Axis-aligned bounding box clipping and span generators.
  • Glyph.Algorithms.Circle: Midpoint stepping with $O(1)$ cross-product vector inclusion testing for arbitrary angular sweeps and pie wedges.
  • Glyph.Algorithms.Triangle: Vertex sorting and DDA scanline edge interpolation.

Glyph.Controllers & Glyph.Display

Display drivers compose controllers, canvas buffers, and HAL transports into an embedded-first object:

  • Glyph.Display.SSD1306: Full facade for 128x64 monochrome OLEDs over HAL.I2C.
  • Glyph.Display.ILI9341: Full facade for 240x320 16-bit color TFTs over HAL.SPI, supporting Framebuffer, Tile_Stream, and Direct_Stream modes.

Transparent Banding (Tile Streaming)

Color displays such as the 240x320 ILI9341 require 153.6 KB of RAM for a full framebuffer—exceeding the memory capacity of many microcontrollers. Glyph solves this with Transparent Banding (Tile_Stream mode):

  • Reduced Memory Footprint: Allocates only a compact horizontal tile buffer (e.g., 240x32 pixels, requiring only ~15 KB RAM).
  • Zero Math for Applications: The user writes normal rendering code using natural screen coordinates (e.g., Y => 150, Y => 280). Glyph’s Render_Scene callback engine partitions the display and translates coordinates into tile offsets automatically.
  • Bit-Exact Output: Output generated via Tile_Stream is mathematically identical to a full in-memory framebuffer.

Hidden Damage Tracking

To maximize I2C and SPI bus throughput, Glyph tracks the minimum dirty bounding box of modified pixels privately inside the display instance. Calling Render flushes only the altered region to the display controller, minimizing bus transmission time.

Desktop Simulator Engine (simulator/)

Glyph includes a native desktop simulator application in simulator/ that runs without physical hardware on macOS, Linux, and Windows:

Key Features:

  • Virtual In-Memory Buses: Implements virtual HAL.I2C and HAL.SPI devices emulating SSD1306 GDDRAM and ILI9341 GRAM registers.
  • Dynamic Target Path: Accepts a target directory argument dynamically: 
    ./simulator/bin/simulator_main /path/to/my_project
  • Multi-Format Media Export: Renders frames into 24-bit BMP images, PPM raster files, animated palette-optimized GIFs, and H.264 MP4 videos using bundled exporter packages.
